# 踩坑记录

002（快手）→ 003（抖音）→ 004（TikTok）→ 005（三合一）一路实际踩过的坑。每条写清楚
**现象 / 原因 / 做法**，「出处」是当时的插件或提交号；002/003/004 的代码已经移出工作区，
要看原文用 `git show <提交号>` 或 `git log -- 003DouyinCreatorArchiver/`。

做新平台之前先过一遍这份清单。

## 一、采集：拿到的数据不对

### 1. 别的页面的作品混进来

- **现象**：在 A 的主页采集，结果里出现不认识的人的视频（TikTok），或者 A 点赞过的视频（抖音）。
- **原因**：页面在后台还会发别的接口——TikTok 首页推荐流 `/api/recommend/item_list`、
  转发流、故事流；抖音切过「点赞」标签后残留的 `aweme/favorite` 回包。旁路采集只要
  「长得像作品」就收，就会混进来。003/004 一度有个「分类不到的回包（other）直接放行」的
  例外，正是漏洞本身。
- **做法**：
  - 只转发明确认识的接口，不做「内容看着像就收」的嗅探；
  - 每条作品按**作者 id**和主页主人比对，对不上就丢（005：抖音 `author.sec_uid`、
    TikTok `author.uniqueId`、快手 `author.id`）；
  - 首屏状态对象里拿不到作者 id 的作品不收（首屏里常夹着推荐内容）。
- **出处**：003、004 上线后发现；005 改成「接口白名单 + 作者 id 比对」。

### 2. 图集作品下成了一段纯音频

- **现象**：图集（多图 + 背景音乐）作品，下下来是个 mp4，只有声音没有画面。
- **原因**：图集作品的接口数据里，除了 `images`，还附带一个给老客户端用的「兼容视频」
  字段，取到手常常是纯音轨。判断「是视频还是图集」时视频字段优先，就被它抢走了。
  还有第二层：同一个作品先后被两次回包捕获，第一次没带 `images`，被判成视频；第二次补全了
  `images`，但 `kind` 没跟着重算，一直锁死在「视频」。
- **做法**：有真实图片就按图集处理；合并多次回包后**重新判定一次** `kind`。
- **出处**：003 上线后发现，004/005 内置。

### 3. 「解析成功」但抓的字段是错的

- **现象**：面板显示采集正常，下载出来全是 `.html`。
- **原因**：以为 TikTok 视频直链在 `tiktokcdn.com` 这类 CDN 域名下，实际挂在
  `v16-webapp-prime.tiktok.com`、`www.tiktok.com/aweme/v1/play/` 这些 `tiktok.com` 自己的
  子域名下，下载规则一条都没命中（见「二、下载」第 1 条）。排错时只在「解析出 0 条」时才存
  回包样本，「看似成功其实抓错」的情况永远拿不到原始结构。
- **做法**：每种接口**解析成功也存一份样本**；字段路径以真实回包样本为准，不凭记忆猜。
- **出处**：004。

### 4. 字段改名后整片采不到

- **现象**：某天开始一直「采集 0 条」，但页面正常。
- **原因**：平台改了接口路径或字段名。快手最典型：GraphQL 的 operationName、`photoUrl` /
  `photoUrls` / `photoH265Urls` 来回变。
- **做法**：字段多名兜底；所有已知路径都不命中时，对整个 JSON 扫一遍「长得像作品的对象」
  （有 id + 有视频/图片/标题字段）；再不行就导出回包看结构，不要猜。
  快手直链里带 `pkey=` 的是 CDN 通用签名链，异地也能下，排在前面。
- **出处**：002。

### 5. 首屏那一页作品不走接口

- **现象**：主页前十几个作品采不到，往下滑之后的能采到；或者单视频页什么都采不到。
- **原因**：首屏数据由服务端直接塞进 HTML：抖音 `<script id="RENDER_DATA">`（URL 编码过的
  JSON）、TikTok `<script id="__UNIVERSAL_DATA_FOR_REHYDRATION__">`（老版本 `SIGI_STATE`）、
  快手 `window.__APOLLO_STATE__`。
- **做法**：inject 里除了挂钩 fetch/XHR，再读一遍这些首屏状态；按内容去重，页面加载完再读
  两轮就停。
- **出处**：002/003/004 各自发现。

### 6. inject 比 content 先跑，早期回包丢了

- **原因**：MAIN world 的 inject.js 在 `document_start` 就开始抓包，ISOLATED 的 content
  脚本 `document_idle` 才载入，中间的 `postMessage` 没人收。
- **做法**：inject 里放一个环形缓冲先存着，content 就绪后发「content-ready」握手，inject 再
  一次性补发（content 侧重复发几次握手，防止错过）。
- **出处**：002。

### 7. 抓包本身拖慢页面

- **原因**：信息流里最大最频繁的响应是视频分片和图片，每个都 `clone().text()` 解码一遍；
  XHR 已经是解析好的 JSON 还 stringify 再 parse 一次。
- **做法**：按 `content-type`（video/audio/image/font）和长度（>3MB）直接跳过；不认识的接口
  根本不读响应体。
- **出处**：提交 `df02c1c`。

### 8. 站内跳转把采集结果清空了

- **现象**：TikTok 采集到一半，在主页里点开一个视频再关掉，采集结果没了；当时已经在列表
  底部，重新采集一条都拿不到。
- **原因**：单页应用切换页面不刷新，只改网址。TikTok 点开作品时网址从 `/@作者` 变成
  `/@作者/video/<id>`，被当成「离开主页」清空了。而旁路采集只能拿到页面**正在加载**的数据：
  列表已经全部加载完，再滑也不会重新请求。
- **做法**：只有进入**另一个作者**的主页才清空；去别的页面只收起面板、保留结果。混入风险
  交给作者 id 比对，不靠清空。每个平台都要实测「主页里点开作品时网址怎么变」（抖音是
  `?modal_id=`，路径不变）。
- **出处**：提交 `2b7799d`。

### 9. 自动滚动「数据在涨、页面不动」或提前收工

- **原因**：
  - 很多主页是整页不滚，作品流在一个自己 `overflow:auto` 的容器里，只滚 window 没用；
  - 有的虚拟列表只认 `wheel` 事件；
  - 标签页切到后台时浏览器会限速懒加载，几轮没新数据不代表到底了；
  - 设了总轮数上限，高产作者滑不到底就停了。
- **做法**：找面积最大的前 3 个可滚动容器连同 window 一起滚，再补一个 `wheel` 事件；后台
  时不计「空转」；不设总轮数，连续 4 轮没新作品才停；节奏 2.8~5.5 秒加随机回滚，别像机器。
- **出处**：002 起；005 去掉轮数上限。

## 二、下载：直链下不下来

### 1. 直链要登录态 Cookie，`chrome.downloads` 又不能自定义请求头

- **现象**：下载出来是 `.html`（验证/拦截页）。
- **原因**：一部分 CDN 直链不带登录态 Cookie 和 Referer 会被拦。`chrome.downloads.download()`
  不支持自定义请求头。
- **做法**：用 `declarativeNetRequest` 在网络层改头：
  - 静态规则（rules.json）补 Referer/Origin；
  - 动态 session 规则塞 Cookie：`chrome.cookies.getAll({domain})` 读出真实 Cookie 拼成请求头；
  - 主域名（`douyin.com`、`tiktok.com`）单独一条规则，`resourceTypes` **不含**
    `xmlhttprequest`，不碰页面自己发的接口请求；
  - 排查规则有没有命中：在扩展的 service worker 控制台跑
    `chrome.declarativeNetRequest.getMatchedRules()`。
- **出处**：004 发现，003 跟进。

### 2. Cookie 规则过一阵就失效，重启浏览器又好了

- **原因**：用 `setInterval` 定期刷新 Cookie。MV3 的 service worker 闲置会被系统杀掉，
  计时器跟着没了，之后再也不刷新；重启浏览器等于重新拉起 service worker，又刷新了一次。
- **做法**：定期任务一律用 `chrome.alarms`（被杀了也会被唤醒），再加 `cookies.onChanged`
  按平台合并触发。
- **出处**：004。

### 3. 队列卡在「排队中」永远不开始

- **原因**：每次真正下载前要等 Cookie 规则刷新完成；刷新偶尔卡住（并发重复调用、Chrome 内部慢），
  整条队列跟着卡死。
- **做法**：刷新加去重（同一时刻只跑一个，其它调用等同一个 promise）+ 3 秒超时，超时就先下。
- **出处**：003。

### 4. CDN 个别节点回网页，存成 `.html` 后被浏览器拦住、占着并发名额

- **现象**：下载栏里一堆「已阻止」的 `.html`；有时队列停在「下载中 2」不动。
- **原因**：同一个视频有十几个候选直链，落在不同 CDN 边缘节点上，个别节点即使 Cookie/Referer
  都对也回验证页。被存成 `.html` 后，Chrome 当成危险文件拦下，可能一直挂在「等用户确认」，
  不完成也不失败，白占一个并发名额。
- **做法**：多候选直链，失败换下一个；005 在 `downloads.onDeterminingFilename`（拿到响应头、
  还没写盘）时看 `mime`，是 `text/html` 就直接取消，走正常的「失败换链」。
- **坑中坑**：一旦注册了 `onDeterminingFilename`，`download()` 里给的 `filename` 不一定还算数
  ——本扩展发起的下载要在监听里用 `suggest({filename, conflictAction})` 把路径再给一次；
  别的扩展、用户自己的下载原样 `suggest()` 放行。
- **出处**：003/004 只能当噪音；005 解决。

### 5. 文件名撞车，出现一堆 `xxx (1).mp4`

- **原因**：同一句文案发好几条、同一天发好几条都常见，「日期_标题」会撞名；连点两次「下载全部」、
  两个标签页各点一次，同一个文件入队两遍，`uniquify` 再存出 `(1)`。
- **做法**：作品 id 编进文件名（`日期_标题_<id>.mp4`）；入队时按目标路径跳过已在排队或正在下的。
  这样文件名里的 id 也成了「从磁盘恢复已下记录」的依据。
- **出处**：002；提交 `1532ff8`。

## 三、存储与性能：用久了浏览器变卡

### 1. 整条队列存一个键，Chrome 常年狂写硬盘

- **现象**：Chrome 主进程长期 25~50MB/s 写盘。
- **原因**：下载队列是一个数组存在同一个 `chrome.storage` 键下（抖音那边积到 15596 条 / 93MB），
  每下完一条就整块重写一遍，LevelDB 被逼着不停 compaction。
- **做法**：一个任务一个键 `q:<补零序号>`，入队写自己、开始下载记下 downloadId、下完才删。
  每次只写几百字节。
- **出处**：提交 `1532ff8`。

### 2. service worker 被回收，任务丢了或重下

- **原因**：任务一出队就从盘上删掉，下到一半 service worker 被回收，完成事件没人接。
- **做法**：任务下完之前一直在盘上，并记下 downloadId；重新拉起时问 Chrome 那一条的状态：
  已完成 → 补记「已下」并收尾，不重下；还在下 → 接着盯；中断/找不到 → 重新排队。
  载入队列只在 service worker 顶层做一次（以前 onStartup/onInstalled/顶层三处并发 resume）。
- **出处**：提交 `1532ff8`。

### 3. 下载记录攒到几十万条，浏览器启动卡、平时卡

- **原因**：`chrome.downloads` 每个文件都在 Chrome 下载历史留一条，Chrome 从不自动清；
  记录到二十多万条时 History 库两百多 MB。
- **做法**：结束的下载攒够 200 个、或队列跑空 10 秒后扫一遍，只 `erase` 本扩展发起、已结束、
  不在下载中的记录（只删记录，不删文件）；浏览器启动、扩展重载时再扫一遍兜底。
  按开始时间分页翻，存量再多也不会一口气全读进来。
- **限制**：只能清自己扩展的记录；换扩展（比如 003 → 005）前要让旧扩展先清一遍。
- **出处**：提交 `7721c3a`。

### 4. `downloaded.txt` 写不出来，或者下载栏刷屏

- **原因**：第一版用 `setTimeout` 防抖 4 秒后写——这 4 秒里 service worker 可能被杀，永远写不出；
  改成每下完一条就写，一批视频连续下完，下载栏刷一串提示。
- **做法**：靠真实事件攒批：同一作者攒够 5 条、或整条队列跑空，才写一次。
- **出处**：003/004。

### 5. 换扩展后旧记录丢了，还会把旧 `downloaded.txt` 冲掉

- **原因**：新扩展的 id 不同，`chrome.storage` 是空的，读不到旧扩展的记录；而 `downloaded.txt`
  是按 storage 里的作者记录**整份覆盖写**，路径又和旧扩展一样，一写就把旧的冲掉。
- **做法**：开始下载前先「从磁盘导入」：读每个作者文件夹的 `downloaded.txt`，再从文件名
  `…_<id>.mp4`、图集文件夹名 `…_<id>` 里补 id。两个会写同一份 txt 的扩展不能同时启用。
- **出处**：005。

### 6. 去重键、规则 ID 跨平台冲突

- **原因**：三个平台合进一个扩展后，`dl:<id>` 可能同名；抖音、TikTok 的动态 Cookie 规则 ID
  都是 9001/9002，会互相覆盖。
- **做法**：去重键带平台前缀 `dl:<platform>:<id>`、`arc:<platform>:<author>`；规则 ID 分段
  （快手 1xxx、抖音 2xxx、TikTok 3xxx）；`requestDomains` 严格限本平台域名，不把一家的
  Cookie 带去另一家。
- **出处**：005。

## 四、扩展机制本身

| 坑 | 原因 | 做法 |
|---|---|---|
| 扩展重新加载后，页面里的面板一点就报 `Extension context invalidated`，控制台刷屏 | 页面没刷新时 `chrome.runtime.sendMessage` 会**同步抛错**，不是 reject，`.catch()` 接不住 | 包一层 try/catch，失效后停掉轮询、提示刷新页面 |
| 后台广播的队列数字，页面面板收不到 | `chrome.runtime.sendMessage` 只发给扩展自己的页面（popup 等），到不了 content 脚本 | 面板在页面可见时轮询 `getState`；`paused` 这类存进 storage 的再监听 `storage.onChanged` |
| CSP 严格的页面上报错 | content 里补一个 `<script src=inject.js>` 当兜底注入，会被页面 CSP/Trusted Types 拦 | 只用 manifest 的 `world: "MAIN"`（Chrome 111+），删掉兜底 |
| 面板样式被页面的 reset 样式破坏 | 面板直接挂在页面 DOM 里 | Shadow DOM + constructable stylesheet（`adoptedStyleSheets`，也不受页面 `style-src` 限制）；定位写在宿主元素的内联 `!important` 上 |
| 选文件夹时 Chrome 提示「将 84349 个文件上传到此网站」 | `<input webkitdirectory>` 的固定措辞（其实什么都不上传），而且要把全部文件列完才回调 | 用 `showDirectoryPicker()`：提示是「查看文件」，可以边遍历边处理 |
| 在 popup 里放文件选择，一选文件 popup 就关了 | popup 失去焦点就关闭 | 文件选择放在独立的扩展页面里，popup 只放入口按钮 |

## 五、平台本身的限制（插件绕不开）

- **抖音**：不登录只能看到前 20 个作品。
- **TikTok**：大多数账号默认不公开点赞列表。
- **快手**：网页端不稳定，扫码登录后经常掉登录、接口报错；接口和字段改得随意。
- **所有平台**：自动滚动会触发风控验证码，要分批跑；保存路径受 `chrome.downloads` 限制，
  只能是「下载目录」下的子文件夹。
